# Methodology

## 1. Dataset catalogue and configuration
The system exposes a curated catalogue of datasets, predictive models, and counterfactual techniques through a single configuration module. Each dataset entry enumerates the CSV path, target label, class vocabulary, optional columns to drop, and per-feature types, while the model and counterfactual maps define the selectable options surfaced in the UI. This central registry keeps the pipeline plug-and-play—adding a dataset or estimator only requires updating the configuration payload used by both the backend services and the frontend controls.【F:backend/app/config.py†L2-L199】

## 2. Data loading, profiling, and metadata synthesis
When a session references a dataset for the first time, the `ModelManager` loads the raw file, applies configuration-driven column pruning, label-encodes the target, and prepares the feature matrix with one-hot encoding for categorical attributes. As part of this process the manager computes rich feature summaries—type inference, distribution statistics, representative categories, and inferred immutability hints—that seed downstream LLM prompts and feasibility defaults. The resulting dataset bundle caches train/test splits, feature names, encoders, and the derived metadata for reuse across requests.【F:backend/app/model_manager.py†L18-L152】

## 3. Predictive modelling lifecycle
The `ModelManager` lazily trains or reloads the requested classifier (MLP, random forest, logistic regression, XGBoost, or decision tree), persisting fitted estimators to disk so subsequent sessions can reuse them. During inference, incoming user responses are normalized with the dataset schema: the manager enforces declared data types, reinstates dropped columns, aligns one-hot encodings with the training feature order, imputes missing values, and finally emits the model's class prediction. This shared lifecycle keeps training, caching, and inference logic consistent for every supported model family.【F:backend/app/model_manager.py†L181-L321】

## 4. LLM-guided user interaction loop
A Flask service orchestrates interactive data collection and explanation. When a user starts a session, the backend validates selections, seeds per-session state, triggers feasibility pre-computation, and immediately returns the first prompt generated by a LangChain+Ollama chain tuned to ask conversational, feature-specific questions. Each submitted answer advances the session until all features are collected, at which point the backend assembles the user's instance, requests a prediction, and prepares counterfactual reasoning. Parallelly, a second LLM chain receives the final model outputs plus recommended changes to draft a plain-language narrative for the user.【F:frontend/app.py†L13-L272】【F:backend/app/chains.py†L1-L56】

On the client, a single-page interface manages the conversation loop. Vanilla JavaScript wires the dropdown selections, session lifecycle, progress indicator, and result rendering by calling the Flask endpoints, updating questions, and populating prediction, counterfactual, and feasibility panels as responses arrive.【F:frontend/static/js/script.js†L1-L318】

## 5. Counterfactual generation
For counterfactual explanations the manager currently integrates the Foil Trees method. It marshals the processed feature order, obtains the trained model, constructs a domain mapper over the training data, and invokes the Foil Trees explainer on the model's probability surface. The raw feature deltas returned by the explainer are then routed to the feasibility layer for validation before being surfaced to the user.【F:backend/app/model_manager.py†L323-L389】

## 6. Automated feasibility constraint synthesis and enforcement
Feasibility governance is handled by the dedicated `FeasibilityModule`. At startup it seeds default constraints and, whenever metadata is available, queries the `LLMConstraintGenerator` to derive dataset-specific immutable sets, bounded ranges, and categorical limits from the summarized feature statistics. The module merges LLM output with fallbacks, caches the resulting rules, and exposes an `enforce` routine that filters raw counterfactual edits: it normalizes feature labels, coerces value types, rejects violations, applies necessary adjustments, and verifies that the refined instance still flips the model's prediction. The generated report captures feasibility, adjustments, and outstanding issues for presentation.【F:backend/feasibility/llm.py†L1-L114】【F:backend/feasibility/module.py†L1-L198】

## 7. Presentation of results and feasibility insights
After enforcement, the backend packages the sanitized counterfactuals, feasibility status, adjustment/violation logs, and natural-language explanation into the response payload. The frontend renders prediction cards, the recommended feature changes, a feasibility badge with detailed bullet lists, and the generated explanation. This closing stage gives end users actionable guidance plus transparency into why certain edits were applied or rejected by the feasibility gatekeeper.【F:frontend/app.py†L200-L272】【F:frontend/static/js/script.js†L202-L318】
